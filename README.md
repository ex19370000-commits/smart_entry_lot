# サービス設計書：Smart Entry Lot（スマート・エントリー・ロット）

## 1. サービス概要

### 1-1. サービス名
**Smart Entry Lot（スマート・エントリー・ロット）**

### 1-2. サービス内容
LINEログイン、SMS認証、Cookie監視を組み合わせた、**「単体完結型」の抽選応募・管理プラットフォーム**です。
※既存のチケット業者やECサイトとのシステム連携（API疎通等）は行わず、本アプリ単体で抽選イベントの作成から応募受付までを完結させます。

### 1-3. 解決する課題
ボットや組織的な多重申込によって当選確率を奪われ、正当な購入機会を逃しているファンの課題を、物理的な身元確認（SMS）とブラウザの個体識別（Cookie）によって解決します。

---

## 2. アイデアの背景

### 2-1. きっかけとなった体験・感情
限定アイテムやチケットの抽選に参加する際、どれだけ正攻法で準備しても「落選」が続く一方で、SNSではボットを駆使した大量当選報告が目立つ現状に強い不条理を感じてきました。「本当に欲しい人に届かない」という怒りと違和感が原動力です。

### 2-2. なぜそれが「気になった」のか
デジタル化で便利になるはずのシステムが、一部の層にハックされている現状はシステムの設計ミスであると感じました。ファンの期待を裏切らない、正直者が報われる仕組みを作りたいと考えました。

---

## 3. 課題の整理

### 3-1. 表に見えている困りごと
- 組織的な多重申込やボットによる、一般ファンの当選確率の著しい低下。
- 転売目的の買い占めにより、本来の定価でサービスを享受できない。
- 抽選システムに対するユーザーの不信感。

### 3-2. 本当に解決したい課題
不正を経済的・技術的に「割に合わないもの」にし、純粋なファンが自分にもチャンスがあると感じられる健全な参加環境を構築すること。

---

## 4. 想定ユーザー

### 4-1. 想定しているユーザー
- **年齢層：** 10代〜50代（限定コンテンツに敏感で、不正に強い不満を持つ世代）
- **生活・状況設定：** 特定商品で、限られた予算と時間の中で正当に商品を入手したいと考えている人。
- **環境設定：** リリース直後に数万件のアクセスが集中するオンラインショップやイベント予約。

### 4-2. 自分とユーザーの距離
私自身が実体験として落選と不条理を経験しているため、ユーザーの不快感やニーズを深く理解しています。

### 4-3. 実際に使われる可能性について
- **最初の人：** 特定の店舗やオンラインショップを利用するファン。
- **場面：** 店舗のSNSで抽選の告知を見た瞬間、またはQRコードを見た時。
- **代替手段：** Googleフォーム、標準的なECサイトの抽選機能。
- **置き換える理由：** 既存ツールでは防げないブラウザの切り替えや複数アカウントの利用を、CookieとSMSの二重監視によって阻止できるため。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ
- **きっかけ：**どうしても手に入れたい限定アイテムの抽選販売告知を見つけ、申し込み用URLをクリックした時。
- **最初の一歩：** LINEログインを行い、初回のみSMS認証を済ませる。これにより、自分が一人のファンであることを証明しエントリーを完了させる。
- **使い続ける理由：** 不正が排除されているという納得感を持って結果を待てるため。また、一度登録すれば次回以降の入力を省ける利便性と信頼感が醸成されるため。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査
| サービス名 | 特徴 | 比較・差別化 |
| :--- | :--- | :--- |
| **LivePocket** | 大規模向け認証強度 | 導入ハードルが高いため、本アプリは「より手軽な単体利用」をターゲットとする。 |
| **Googleフォーム** | 無料・即座に開始可能 | 認証が脆弱。本アプリは「Googleフォームの手軽さ」と「強固な認証」を両立させる。 |

### 5-2. それでも自分が作りたい理由
既存の選択肢には、導入のしやすさと認証の強固さを両立させた、中間層向けのサービスが少ないと感じています。LINEという身近なインターフェースを使いつつ、高いセキュリティを標準化した仕組みを提供したいと考えました。

### 5-3. 差別化を一文で表すと
> **「Cookieによる効率的な1次検知と、SMSによる厳格な2次認証を組み合わせ、運営コスト抑制とファンへの公平性を両立させるアプリです。」**

---

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化
- **行動の変化：** 無駄な複数アカウント作成を止め、1つのアカウントで結果を待つようになる。
- **気持ちの変化：** 「どうせ当選しない」という諦めが、「公平な抽選だ」という期待に変わる。
- **考え方の変化：** 公平なシステムの上で「運」に任せるべきだという健全なマインドが醸成される。

### 6-2. 価値を一文で表すと
> **「公平さを大切にするすべての人が、確かな納得感を持って限定アイテムの抽選を楽しめるようになるサービスです。」**

---

## 7. このアプリで実現すること

### 7-1. MVPで作る機能
- LINEログイン連携 (LIFF)
- Cookieを用いた同一ブラウザでのアカウント切り替え検知ロジック
- 初回登録時のSMS認証連携 (Twilio)
- アプリ内完結の抽選申し込みおよび自動抽選実行機能
- 抽選結果のユーザー表示画面

### 7-2. 本リリースで作る機能
- BtoB向けのマルチテナント管理機能（主催者別管理）
- 当選後の権利行使（購入・入場）用QRコード生成
- 管理者用ダッシュボード（不正疑いユーザーの抽出・ブロック機能）
- 抽選結果のLINEプッシュ通知

## 8. このアプリの懸念点とその対策

### 8-1. 攻撃手法に対する防御モデル
1. **ボットによる高速なブラウザ自動操作**
   - **対策：** 1次防壁としてLINEログインを強制。Cookieクリア後も別LINEアカウントの再認証を必須とし、アカウント量産のハードルを上げる。
2. **SMS受信代行サービスやVoIP（050番号）の悪用**
   - **対策：** Twilio Lookup APIを活用。Carrier Typeを判定し、Mobile（携帯回線）のみ許可することで架空アカウントを排除。
3. **物理SIMの大量契約（組織的な力技の攻撃）**
   - **対策：** 経済的抑止力の活用。回線維持コストを強制することで、不正のROI（投資対効果）をマイナスにする。

### 8-2. 開発・運用上の懸念
- **SMS送信コストの肥大化**
   - **対策：** すべてのアクセスに即座にSMS認証を要求するのではなく、まずはLINE連携とCookieによる個体識別を行い、不審な挙動を検知した際や最終的な応募確定時のみに限定して実行することで、APIコストを最小限に抑えます。
- **LINE内ブラウザのCookie制限**
   - **対策：** LINE内ブラウザの仕様によりCookieが保持されにくいケースを想定し、LocalStorageやFingerprintJSなどを用いた補完的な識別手法を検討し、精度の向上を図ります。

## 10. 技術スタック

### 10-1. 使用予定の技術
- **Framework:** Ruby on Rails 7
- **Database:** MySQL 8.0
- **Infrastructure:** AWS (EC2, RDS), Docker
- **Library:** line-bot-api, twilio-ruby, sidekiq, redis

### 10-2. 技術選定の理由
- **理由：** 実務での標準的な構成であるRails×AWSを習得するため。また、API連携（LINE, Twilio）や非同期処理（Sidekiq）といった必須スキルを網羅できるため。
- **チャレンジ：** Cookieによる端末識別と外部認証APIを組み合わせた堅牢なガードロジックの構築。
- **不安な点：** LINE内ブラウザでのCookieの永続性や、大量リクエスト時のSidekiqのパフォーマンス管理。

### 10-3. キャッチアップ不足の懸念
- 外部API連携時の例外処理とセキュリティ設計。
- 大規模アクセスを想定した非同期処理（Sidekiq/Redis）の最適化。
