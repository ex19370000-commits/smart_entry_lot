# randomizer
1. サービス概要
1-1. サービス名
Smart Entry Lot（スマート・エントリー・ロット）

1-2. サービス内容
LINE公式アカウントと連携し、店舗への入店抽選をオンラインで完結させる管理システムです。QRコードからLINEで友だち追加するだけで抽選に申し込め、結果もLINEで通知されるため、店頭での長時間の待機を一切排除します。
最大の特徴は、「ハッシュ値による事前コミットメント」を導入し、店舗側による抽選結果の改ざんが物理的に不可能であることを技術的に証明する点にあります。

1-3. 解決する課題
早朝からの行列によるユーザーの身体的負担と、店舗側のオペレーション負荷を解消します。さらに、既存のデジタル抽選サービスが抱える「店舗側による操作の疑念（ブラックボックス化）」を技術的に解消し、ユーザーと店舗の信頼関係を再構築します。

2. このアイデアはどこから生まれたか
2-1. きっかけとなった体験・感情
休日、限定商品を求めて店舗へ行った際や、趣味でパチンコホールに並びに行った際、数時間前から屋外で並び続け、体力と時間を大幅に消耗しました。また、一部のデジタル抽選を利用した際も「特定の番号が抜かれているのではないか」「店側が有利なように操作しているのではないか」というSNS上の不満や自分自身の違和感を目にし、「利便性と同じくらい『透明性』が重要である」と痛感しました。

2-2. なぜそれが「気になった」のか
私は「論理的な公平性」と「時間の有効活用」を非常に大切にする価値観を持っています。スマートフォンの普及した現代において、いまだに「物理的な拘束」や「不透明な抽選ロジック」が前提となっている日本の店舗運営に強い違和感を覚え、デジタルと日常（LINE）を接続し、根拠を持ってこの不便を解消したいと考えました。

3. 課題の整理
3-1. 表に見えている困りごと
・過酷な天候下での数時間に及ぶ行列待機。
・行列による近隣店舗や歩行者への通行妨害。
・抽選プロセスの不透明さによる店舗への不信感。

3-2. 本当に解決したい課題は何か
・なぜ？：待ち時間の拘束が、ユーザーの自由な時間を奪い、顧客満足度を下げるから。
・なぜ？：不透明な抽選が、店舗のブランドイメージを損なうから。
・なぜ？：アナログな管理や、信頼性の低いデジタル管理が、店舗側とユーザー双方にストレスを生んでいるから。

→ 本当に解決したい課題：
「店舗へ行く」というポジティブな体験を、「過酷な待機」や「運営への不信」から解放し、「技術的に改ざんが不可能な抽選」を提供することで、顧客と店舗の双方に心理的・時間的なゆとりを提供すること。

4. 想定ユーザーについて
4-1. 想定しているユーザー
・年齢： 20代〜60代。LINEを日常的に使う層。
・生活・状況： 週末や早朝を有効活用したいと考えている、効率性を重視する消費者。
・環境： 物理的な待機場所が確保しにくい都市部の店舗や、限定イベントを行う店舗や、ホール運営を行う店舗。

4-2. 自分とユーザーの距離
自分自身
私自身がこの課題の当事者であり、既存の「ただ並ばせるだけ」または「便利だが不透明な」仕組みに限界を感じているため、ユーザー目線で最も信頼できる導線を設計できると考えています。

4-3. 実際に使われる可能性について
・最初の人： 特定の店舗に通うファン、公平なルールを重視する層。
・場面： 店舗のSNSで抽選の告知を見た瞬間、または店頭でQRコードを見た時。
・代替手段： 店頭での物理的な整列、手書きの整理券、既存の抽選アプリ。
・置き換える理由： 「使い慣れたLINEで完結する」利便性と、「後から結果の正当性を検証できる」圧倒的な透明性。

4-4. ユーザーがサービスを導入して利用するまでのイメージ
・きっかけ： 店舗の公式LINEから「抽選開始」のメッセージが届く。
・最初の一歩： LINE内のリッチメニュー（ボタン）から抽選画面（LIFFアプリ）を開き、1タップで申し込む。
・使い続ける理由： 抽選結果がLINEで自動通知され、当選後の入店もLINEの画面を提示するだけでスムーズに行えるため。

5. 既存サービス・競合調査
5-1. 似たサービスの調査
①サービス名： LINE公式アカウント（順番待ち・呼び出し機能）
内容：混雑時に整理券を発行し、順番が来たら通知する仕組み。

②サービス名：抽選くん
内容：LINEから1タップで抽選に申し込み、指定時刻に自動実行される抽選結果を場所を問わず受け取れる仕組み

5-2. それでも自分が作りたい理由
既存の最大手サービスはユーザー側の不正防止には強力ですが、抽選ロジック自体は依然として店舗側のサーバー内で行われるブラックボックスです。本サービスは、暗号学的なアプローチである「事前コミットメント」を導入し、店舗側も後出しで結果を変えられないことを技術的に担保します。「店側が不正をしていないこと」を証明する手段を提供したいと考えました。

5-3. 差別化を一文で決める
ハッシュ値による事前コミットメント】を導入し、店舗側による抽選結果の改ざんが物理的に不可能であることを証明する、「疑われない」抽選システム。

6. このサービスで提供したい価値
6-1. ユーザーの変化
・行動の変化： 店の前で待機する時間がなくなり、近隣のカフェや自宅で自由に過ごせる。
・気持ちの変化： 抽選の公平性を信頼でき、当選発表をストレスなく待てる。
・考え方の変化： 「並んで待つ」という義務から解放され、よりスマートな消費スタイルが定着する。

6-2. 価値を一文で表す
「このサービスは、行列の不便を感じる人が、日常的に使うLINEを通じて公平かつ自由に権利を得ることができるサービス」

7. このアプリで実現すること
MVPで作る機能
・LINE連携によるログイン（LIFF）
・抽選申し込み機能
・指定時間での自動抽選実行（Sidekiq + Redis）
・抽選結果表示画面
・抽選結果の正当性検証画面（終了後、シードを公開し、事前公開ハッシュとの一致を確認可能にする）
・抽選シードの事前ハッシュ公開機能（抽選実行前に、結果を決定づける「種」のハッシュ値を公開）

本リリースで作る機能
・Messaging APIによる抽選結果のLINE通知
・管理者用ダッシュボード（当選者管理・CSV出力）
・不正申し込みの監視・制限機能
・当選後の入店確認用QRコード表示機能

8. このアプリの懸念点とその対策
懸念点①
何が問題になりそうか： 抽選実行時にDBへの負荷が集中すること。

対策：抽選処理は非同期（Sidekiq）で実行し、結果をMySQLに保存。
ユーザーには保存済みの結果を表示させることで、動的な計算を最小限に抑え、参照速度を向上させる。
MySQLのインデックスを最適化し、数万件の申し込みがあっても瞬時に検索・表示できる設計にする。

懸念点②
何が問題になりそうか： 抽選の「正当性の証明」という概念が一般ユーザーには難解であること。

対策： UI上で「デジタルな未開封の封筒」といったメタファーを用い、検証ボタン一つで「改ざんがないこと」を誰でも直感的に確認できる演出を行う。

9. 今後の展開・発展の方向性
・運用面： LINE内の行動データを分析し、店舗への再来店を促すマーケティング支援機能。
・データ活用： 当選後の入店率を可視化し、店舗が最適な在庫準備を行える仕組み。

10. 技術スタック
10-1. 使用予定の技術
・フレームワーク： Ruby on Rails 7
・DB： MySQL 8.0
・インフラ： AWS (EC2, RDS for MySQL), Docker
・外部API： LINE Messaging API / LIFF
・ライブラリ： Sidekiq, Redis, Digest::SHA256（ハッシュ化用）

10-2. 技術選定の理由
・MySQL: 標準的なRDBとして読み込み速度を重視。将来的なデータ量増加も見据えたインデックス設計を学ぶため。
・LINE API (LIFF/Messaging API): ユーザーの導入ハードルを最低限にしつつ、サーバーからのプッシュ通知というSE的な非同期通信を実装するため。
・AWS: 実務での普及率が高いインフラ構成を構築し、RDSでの堅牢なデータ運用を経験するため。
・Digest::SHA256: 抽選に使用するランダムシードをハッシュ化し、事前に公開するため。これにより、抽選実行後に店舗側が都合よくシードを書き換えてもハッシュ値が一致しなくなるため、改ざん防止を数学的に担保します。

10-3. キャッチアップ不足の懸念
・LINE API (LIFF/Messaging API) の認証と連携

懸念： RailsアプリとLINE側のユーザー識別（UID）の紐付けや、LIFF独自の挙動（ブラウザとLINE内ブラウザのセッションの違いなど）の理解に時間を要する可能性があります。

対策： まずはWebブラウザ単体で動く「通常のログイン機能」を優先して作成し、LINE連携はアドオン形式で実装することで、最悪の場合でもWebアプリとして公開できる状態を死守します。

・Sidekiq / Redis を用いた非同期・バッチ処理

懸念： 「毎日〇時に実行」というスケジューリングや、本番環境（AWS）上でのRedisの安定稼働設定は初挑戦となるため、環境構築で詰まるリスクがあります。

対策： 開発初期段階でDockerを用いたRedis環境を構築し、手動実行による非同期処理のテストを早期に行います。自動実行については sidekiq-scheduler 等のライブラリの調査を並行して進めます。

・Digest::SHA256を用いた公平性の証明ロジック

懸念： 単なる関数の呼び出しだけでなく、「抽選前にハッシュを公開し、終了後にシードを公開して検証する」という一連のプロトコルを、矛盾なくデータ設計に落とし込む必要があります。
過去に実装経験がない為、実装に時間を要する可能性があります。

対策： Rails環境とは切り離した純粋なRubyスクリプトで「シード生成・ハッシュ化・検証」のプロトタイプを早期に作成し、ロジックを確定させます。また、複雑な実装を避け、まずは最小限のステップ（ハッシュ保存とシード公開）での完遂を目指します。

・完成に向けたIssueの見積もりと優先順位

懸念： 残り約4週間という期間で、インフラ構築（AWS）からLINE連携までを完遂するのは非常にタイトです。

対策： 機能を「絶対必要な機能（MVP）」と「あれば良い機能（LINE連携等）」に厳密に分けます。5月11までにWebアプリのコア（抽選機能）を完成させ、最終週をAWSデプロイとLINE連携の調整に充てるスケジュールで進めます。
