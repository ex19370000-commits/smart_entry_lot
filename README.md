. サービス概要

1-1. サービス名
Smart Entry Lot（スマート・エントリー・ロット）

1-2. サービス内容
LINEログインをベースに、SMS認証とCookie監視を組み合わせることで、1人1回の公平な抽選権利を技術的に死守する限定アイテム・チケット向けの抽選管理システムです。

1-3. 解決する課題
ボットや組織的な多重申込によって当選確率を奪われ、正当な購入機会を逃しているファンの課題を、物理的な身元確認（SMS）とブラウザの個体識別（Cookie）によって解決します。

2. このアイデアはどこから生まれたか
2-1. きっかけとなった体験・感情
限定アイテム、チケットを求めて抽選に参加する際、どれだけ早く準備して正攻法で申し込んでも「在庫切れ」や「落選」が続くことに強い落胆を感じてきました。一方で、SNSではボットや大量のアカウントを駆使して数十件の当選を報告する転売目的のユーザーが目立ち、「本当に欲しい人に届かない」という不条理な状況に強い怒りと違和感を覚えました。

2-2. なぜそれが「気になった」のか
デジタル化によって便利になるはずの抽選システムが、技術を悪用する一部の層にハックされ、一般のファンが排除されている現状は、システムの設計ミスであると感じました。
その為、ファンの期待を裏切らない仕組みを作りたいと考えました。

3. 課題の整理
3-1. 表に見えている困りごと
・組織的な多重申込やボットによる、一般ファンの当選確率の著しい低下。
・転売目的の買い占めにより、本来の定価で商品やサービスを享受できない。
・既存の抽選システムに対するユーザーの不信感と、主催者側のブランドイメージ低下。

3-2. 本当に解決したい課題は何か
なぜ？：一部のプロユーザーが大量のアカウントを安価に作成・運用し、確率を操作しているから。
なぜ？：既存の認証（メールアドレスのみ等）が脆弱で、1人1アカウントの原則を簡単に突破できるから。
なぜ？：運営側が「不正のコスト」を上げる仕組みを導入できておらず、正直者が損をする構造になっているから。

→ 本当に解決したい課題：
ボットや組織的な不正を経済的・技術的に割に合わないものにし、純粋にイベントや商品を愛するファンが、自分にもチャンスがあると感じられる健全な参加環境を構築すること。

4. 想定ユーザーについて
4-1. 想定しているユーザー
年齢設定：年齢：10代〜50代
理由：限定コンテンツに最も敏感であり、かつ転売などの不正問題に対して最も強い不満を抱えている世代だからです。
生活・状況設定：
生活・状況：特定商品で、限られた予算と時間の中で正当に商品を入手したいと考えている人。
理由：不正者が有利な現状を打破し、自分のスマホ1台から申し込むことが報われる仕組みを切望しているためです。

環境設定：
環境：リリース直後に数万件のアクセスが集中するオンラインショップや、限定イベントの予約プラットフォーム。
理由：短時間にリクエストが集中する環境下でも、個体識別を正確に行い、不正を瞬時に弾く仕組みが必要です。

4-2. 自分とユーザーの距離
私自身が限定商品やチケットの抽選でボットや転売等により実際に落選した経験がある為、ユーザーが何を求め、何を不快に感じるかを深く理解しているからです。

4-3. 実際に使われる可能性について
・最初の人： 特定の店舗やオンラインショップを利用するファン。
・場面： 店舗のSNSで抽選の告知を見た瞬間、またはQRコードを見た時。
・代替手段： Googleフォーム、標準的なECサイトの抽選機能やアプリ。
・置き換える理由：一般的なツールでは防げないブラウザの切り替えや複数アカウントの利用を、CookieとSMSの二重監視によって低コストで阻止できるためです。

4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)
・きっかけ：特定のブランドやアーティストのSNS、公式サイト等で、どうしても手に入れたい限定アイテムの抽選販売告知を見つけ、申し込み用のURLをクリックした時。
・最初の一歩：LINEログインを行い、画面の案内に従って初回のみSMS認証による本人確認を済ませる。これにより、自分がボットや転売組織ではない一人のファンであることを証明し、エントリーを完了させる。
・使い続ける理由：SMS認証というハードルがある分、逆にボットや多重申込が排除されているという納得感を持って結果を待てるため。また、一度登録すれば次回以降は面倒な入力を省いてスムーズに申し込める利便性があり、このシステムが採用されている抽選であれば安心して参加できるという信頼感が醸成されるため。

5. 既存サービス・競合調査
5-1. 似たサービスの調査
サービス名：LivePocket-Ticket-（ライブポケット）
特徴：業界標準の認証強度を持ち、特定のイベントでSMS認証を強制できる。
課題：大規模イベント向けのため手数料設定や審査があり、個人クリエイターや小規模ブランドが「明日から抽選を始めたい」というスピード感で導入するにはハードルが高い。

サービス名：Shopify Bot Protection（ECサイト向けボット対策）
特徴：大手ECサイトで採用される高度なフィルタリング。
課題：月額料金が高額であり、抽選機能のためだけに導入するにはコスト過多。また、LINEのような国内のSNSプラットフォーム内での完結を前提としていない。

サービス名：Googleフォーム / Formrun（汎用フォーム）
特徴：無料・低価格で即座に開始できる。
課題：メールアドレスのみの認証であるため、ボットによる数千件の多重投稿を事実上放置することになり、後からの「名寄せ作業（重複チェック）」に膨大な人的コストが発生する。

5-2. それでも自分が作りたい理由
既存の選択肢には、導入のしやすさと認証の強固さを高い次元で両立させた、中間層向けのサービスがまだ少ないと感じています。私は、LINEという身近なインターフェースを使いながら、Cookieによる効率的な検知とSMSによる確実な認証を標準化し、どんな規模の主催者でも「安心できる抽選」をすぐに提供できる仕組みを実現したいと考えました。

5-3. 差別化を一文で決める
「このアプリは、Cookieによる効率的な1次検知と、SMSによる厳格な2次認証を組み合わせることで、主催者の運営コストを抑えつつ、ファンの公平な権利を最大化するアプリです。」

6. このサービスで提供したい価値
6-1. ユーザーの変化
行動の変化：複数アカウントを作る無駄な努力を止め、1つのアカウントでじっくり結果を待つようになる。
気持ちの変化：抽選結果が出るまでの期間、「どうせ当選しない」という諦めから、「公平な抽選だ」という期待に変わる。
考え方の変化：公平なシステムの上で「運」に任せるべきだという健全なマインドが醸成される。

6-2. 価値を一文で表す
「このサービスは、公平さを大切にするすべての人が、確かな納得感を持って限定アイテムの抽選を楽しめるようになるサービスです。」

7. このアプリで実現すること
MVPで作る機能
・LINEログイン連携 (LIFF)
・Cookieを用いた同一ブラウザでのアカウント切り替え検知ロジック
・初回登録時のSMS認証連携 (Twilio)
・抽選申し込みおよび自動抽選実行機能
・抽選結果のユーザー表示画面

本リリースで作る機能
・BtoB向けのマルチテナント管理機能（複数の主催者が個別に抽選を作成可能にする）
・当選後の権利行使（購入・入場）用QRコード生成
・管理者用ダッシュボード（不正疑いユーザーの抽出・ブロック機能）
・抽選結果のLINEプッシュ通知

8. このアプリの懸念点とその対策
攻撃手法に対する防御モデル
1. ボットによる高速なブラウザ自動操作
   - 対策: 1次防壁としてLINEログインを強制します。Cookieをクリアしても、新しい申し込みには「別のLINEアカウント」が必要になります。現在のLINEアカウント作成には電話番号が必須であり、アカウントの量産自体が高いハードルとなるため、単純なブラウザ自動化だけでは突破不可能な構造にします。
2. SMS受信代行サービスやVoIP（050番号）の悪用
   - 対策: TwilioのLookup APIを活用し、入力された電話番号の種別（Carrier Type）を判定します。VoIPや仮想番号を弾き、国内の正規の「Mobile（携帯回線）」のみを許可することで、安価な架空アカウントの量産を技術的に防ぎます。
3. 物理SIMの大量契約（組織的な力技の攻撃）
   - 対策: これが本アプリが狙う最終的な「経済的抑止力」です。物理SIMの契約費用・維持費という物理的コストを強制することで、転売による「期待利益」よりも「不正実行コスト（ROI）」を上回らせ、ビジネスとしての多重申込を無効化します。

開発・運用上の懸念
- SMS送信にかかる従量課金コストが、個人の開発規模を超える可能性がある
   - 対策: すべてのアクセスに即座にSMS認証を要求するのではなく、まずはLINE連携とCookieによる個体識別を行い、不審な挙動（同一端末からの頻繁なアカウント切り替え等）を検知した際や、最終的な応募確定時のみに限定して実行することで、APIコストを最小限に抑えます。
- LINE内ブラウザのCookie制限
   - 対策: LINE内ブラウザの仕様によりCookieが保持されにくいケースを想定し、LocalStorageやFingerprintJSなどを用いた補完的な識別手法を検討し、精度の向上を図ります。

9. 今後の展開・発展の方向性

10. 技術スタック
10-1. 使用予定の技術
・フレームワーク： Ruby on Rails 7
・DB： MySQL8.0
・インフラ： AWS (EC2, RDS), Docker
・ライブラリ： line-bot-api, twilio-ruby, sidekiq, redis

10-2. 技術選定の理由
・なぜこの技術を使うのか：実務での標準的な構成であるRails×AWSを習得するため。また、API連携（LINE, Twilio）や非同期処理（Sidekiq）といった、バックエンドエンジニアとしての必須スキルを網羅できるため。
・今回チャレンジしたい点：Cookieによる端末識別と、外部認証APIを組み合わせた堅牢なガードロジックの構築。
・不安な点：LINE内ブラウザでのCookieの永続性や、大量リクエスト時のSidekiqのパフォーマンス管理。

10-3. キャッチアップ不足の懸念
・外部API連携時の例外処理とセキュリティ設計。
・大規模アクセスを想定した非同期処理（Sidekiq/Redis）の最適化。
